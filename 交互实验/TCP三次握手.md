# TCP 三次握手模拟

TCP 是面向连接的协议。连接建立不是“打个招呼”，而是双方交换初始序列号并确认彼此的收发能力。这个实验把三次握手的报文、状态与序号变化逐步展示出来。

## 三次握手的必要步骤

| 步骤 | 方向 | 报文 | 关键字段 | 发送方状态变化 |
| --- | --- | --- | --- | --- |
| 1 | 客户端 → 服务端 | SYN | `seq = c` | CLOSED → SYN_SENT |
| 2 | 服务端 → 客户端 | SYN + ACK | `seq = s, ack = c + 1` | LISTEN → SYN_RCVD |
| 3 | 客户端 → 服务端 | ACK | `ack = s + 1` | SYN_SENT → ESTABLISHED |
| — | 服务端收到 ACK | — | — | SYN_RCVD → ESTABLISHED |

SYN 与 FIN 都会消耗一个序列号，因此确认号要加 1；普通数据报文不额外消耗序号（除非携带数据）。

## 为什么不是两次

假设只有两次握手：客户端发送 SYN，服务端回复 SYN-ACK 后即认为连接建立。此时服务端无法确认客户端是否收到了自己的 SYN-ACK，也无法确认客户端的接收能力。更严重的是，网络中延迟的旧 SYN 可能让服务端建立一个早已失效的连接。

第三次 ACK 让服务端确认“客户端确实收到了我的 SYN，并且愿意继续”。这就是“三次”而不是“两次”的根本原因。

::: warning 半连接与 SYN Flood
服务端收到 SYN 后进入 SYN_RCVD 并分配资源，如果客户端始终不发送最后的 ACK，就会形成半连接。SYN Cookie 通过把状态编码进序列号，避免为半连接立即分配大量资源。
:::

## 序号与确认号

- **序列号（seq）**：本报文第一个字节在整个字节流中的位置。
- **确认号（ack）**：期望收到的下一个字节，表示“这个序号之前的数据都已收到”。

示例中客户端初始序号 $c = 1000$：

- 客户端发送 `SYN, seq=1000`。
- 服务端回复 `SYN, seq=2000, ack=1001`。
- 客户端回复 `ACK, ack=2001`。

三次握手完成后，双方可以从各自的初始序号开始传输数据。

## 思考题

1. 如果第三次 ACK 丢失，客户端和服务端分别处于什么状态？会发生什么？
2. 为什么初始序列号要随机化，而不是从 0 开始？
3. 四次挥手中为什么需要 `TIME_WAIT`？它和三次握手有什么对称性？
4. 如果网络中存在延迟的旧 SYN，三次握手如何避免建立错误连接？
